# 폰 카메라 슬로우모션 기반 스윙 분석 시뮬레이터 — 설계 및 기술 조사

> 목적: 트랙맨 같은 상용기 없이, **스마트폰 슬로우모션 영상만으로 골프 스윙의
> 클럽 딜리버리 지표(스윙 패스·어택앵글·헤드 스피드 등)를 측정**하는 시뮬레이터의
> 실현 가능성과 설계를 정리한다. 본격 개발 착수 전 기술 검증(feasibility) 문서.

---

## 1. 측정 목표와 우선순위

폰 1대(2D 단일 카메라)로 얻을 수 있는 지표를 신뢰도 순으로 구분한다.
핵심 통찰: **스핀은 공의 미세 회전(1000fps+ 필요)이라 불가**하지만,
**패스·어택앵글·페이스는 "클럽의 기하학적 자세"라 카메라가 직접 관측 가능**하다.

| 지표 | 우선순위 | 신뢰도 목표 | 필요 뷰 | 비고 |
|---|---|---|---|---|
| 헤드 스피드 | P0 | 상 (±3%) | DTL / 정면 | 캘리브레이션 스케일 필수 |
| 스윙 패스 (인아웃/아웃인) | P0 | 상 (±1~2°) | DTL / 오버헤드 | 임팩트 존 궤적 각도 |
| 어택앵글 (다운/업블로) | P1 | 중상 (±2°) | 정면 / DTL | 로우포인트 검출 |
| 스윙 플레인 / 템포 | P1 | 중 | DTL | 시각화 위주 |
| 페이스 앵글 (오픈/클로즈) | P2 | 참고용 (±3°+) | 정면 근접 | 모션블러·프레임 부족이 벽 |
| 페이스 투 패스 | P2 | 참고용 | 조합 | 오차 누적 |
| 볼 스피드 / 발사각 | P1 | 중 | 정면 | 공 추적 |
| 스핀 / 정밀 비거리 | — | 불가 | — | 물리모델 추정만 가능 |

**설계 결론:** MVP는 **P0(헤드 스피드 + 스윙 패스)**에 집중하고,
P1(어택앵글)까지 확장한다. 페이스 앵글은 "조건부 참고값"으로만 노출한다.

## 2. 항목별 측정 원리

### 2.1 헤드 스피드
- 임팩트 직전 N프레임에서 헤드 중심의 픽셀 이동량을 측정.
- `속도 = (픽셀 이동량 × 스케일[m/px]) / (프레임수 / fps)`
- 예: 240fps, 헤드가 2프레임에 40px 이동, 스케일 0.01 m/px
  → (40 × 0.01) / (2/240) = 0.4 / 0.00833 = **48 m/s ≈ 173 km/h**
- 오차 요인: 모션블러로 헤드 중심 검출이 흔들림 → 서브픽셀 보정 + 다중 프레임 회귀로 완화.

### 2.2 스윙 패스 (인아웃 / 아웃인)
- **DTL 또는 오버헤드 뷰**에서 임팩트 존(공 좌우 약 ±15cm) 헤드 궤적을 직선 근사.
- 그 직선과 **타겟라인(캘리브레이션 시 지정)**의 각도차가 패스.
- 우상향(타겟 오른쪽으로 진행) = 인투아웃(+), 좌향 = 아웃투인(−).
- 정확도 핵심은 **카메라가 타겟라인 연장선상에 정확히 정렬**되는 것.
  → 정렬 오차 보정을 위해 지면 기준물(정렬 스틱, 격자 매트) 필요.

### 2.3 어택앵글 (다운블로 / 업블로)
- 헤드의 **수직 궤적 기울기**를 임팩트 지점에서 계산.
- 임팩트 전후 헤드 높이(y)를 추적 → 궤적을 2차 곡선 피팅 → 임팩트 x에서의 접선 기울기 = 어택앵글.
- 하강 중(−) = 다운블로, 상승 중(+) = 업블로.
- **로우포인트(최저점)**가 공보다 앞(타겟쪽)이면 다운블로로 교차검증.
- 정면 뷰에서 잘 보이며, DTL로도 보조 측정 가능.

### 2.4 페이스 앵글 (제한적)
- 임팩트 순간 페이스 법선 방향을 추정 → 타겟라인 대비 오픈/클로즈.
- **문제:** 페이스는 150km/h+로 움직여 240fps에서 임팩트 프레임 1~2장, 모션블러 심함.
- **완화책:** 헤드에 고대비 정렬 마커(스티커) 부착 + 480~960fps + 강한 조명(빠른 셔터).
- 그래도 ±2~3° 이상 오차 → **참고용 표시, 신뢰구간 함께 노출**.

## 3. 카메라 셋업 (두 뷰 모두 지원)

| 항목 | 다운더라인(DTL) | 정면(페이스온) |
|---|---|---|
| 위치 | 공-타겟 라인 뒤 연장선, 손높이 | 타겟라인과 직각, 공 정면 |
| 거리 | 2.5~4 m | 2.5~4 m |
| 강점 | 스윙 패스, 스윙 플레인 | 어택앵글, 로우포인트, 체중이동 |
| 필수 기준물 | 정렬 스틱(타겟라인), 매트 격자 | 지면 수평선, 공 위치 마커 |

**공통 촬영 요구사항**
- **프레임레이트:** 최소 240fps, 페이스 측정 시 480fps+ 권장.
- **셔터/조명:** 모션블러 최소화를 위해 밝은 환경(실외 또는 강한 조명). 셔터 우선.
- **삼각대 고정** 필수 (핸드헬드 시 흔들림이 각도 오차로 직결).
- **캘리브레이션 기준물:** 알려진 치수의 격자 매트 또는 정렬 스틱(길이 기지).
- **해상도:** 960fps는 대개 720p 이하로 떨어지므로 240/480fps + 1080p 균형이 실용적.

## 4. 캘리브레이션 (정확도의 90%)

단일 2D 카메라의 최대 약점은 **스케일과 투영 왜곡**. 이를 잡는 게 정확도의 핵심.

1. **스케일 캘리브레이션:** 프레임 내 기지 치수 물체(격자 한 칸 = 실측 cm)로 `m/px` 산출.
   깊이에 따라 스케일이 달라지므로 **스윙 궤적이 지나는 평면 기준**으로 보정.
2. **평면(호모그래피) 보정:** 지면/스윙 평면에 대한 원근 왜곡을 4점 대응으로 펴기(warp).
3. **타겟라인 지정:** 사용자가 UI에서 타겟라인 2점을 찍어 기준각 0° 정의.
4. **렌즈 왜곡 보정(선택):** 광각/초광각 렌즈면 배럴 왜곡 보정 계수 적용.

> 캘리브레이션 없이는 "속도·각도 절대값"을 못 구한다. 상대적 스윙 비교만 가능.

## 5. 처리 파이프라인

```
[슬로우모션 영상]
      │
      ▼
1. 프레임 추출        ffmpeg (fps 유지, 타임스탬프 보존)
      │
      ▼
2. 캘리브레이션       기준물 검출 → 스케일/호모그래피/타겟라인
      │
      ▼
3. 객체 추적          클럽 헤드·공 검출 및 프레임별 위치 추적
      │                 (색/모션 기반 + 옵션: 경량 검출 모델)
      ▼
4. 임팩트 검출        공 이탈 프레임 / 헤드-공 최근접 프레임 탐지
      │
      ▼
5. 지표 계산          헤드스피드·패스·어택앵글·(페이스)
      │                 궤적 곡선 피팅 + 접선/각도 산출
      ▼
6. 물리 모델(선택)    발사 조건 → 예상 비거리 추정(참고값)
      │
      ▼
7. 결과 시각화        궤적 오버레이 + 수치 + 신뢰구간
```

## 6. 기술 스택 후보

### 방식 A — 웹(브라우저) 우선  ← MVP 추천
- **장점:** 설치 불필요, 크로스플랫폼, 빠른 반복. 영상 업로드/분석형에 적합.
- **구성:**
  - 프레임 처리: `ffmpeg.wasm` 또는 서버측 ffmpeg
  - 추적/비전: **OpenCV.js** (색·윤곽·옵티컬플로우), 또는 **TensorFlow.js**(경량 검출)
  - 렌더: `<canvas>` 궤적 오버레이
  - 실시간 카메라: `getUserMedia` (단, 브라우저는 대개 고fps 슬로우모션 접근 제한 → **녹화 후 업로드 분석** 방식이 현실적)
- **한계:** 브라우저에서 240/960fps 라이브 캡처는 어려움 → 폰 기본 카메라로 슬로우 촬영 후 업로드.

### 방식 B — 네이티브 앱
- **iOS:** AVFoundation(고fps 캡처) + **Vision**/CoreML + Metal.
  iPhone은 240fps(1080p) / 일부 모델 슬로우모션 지원이 안정적.
- **Android:** CameraX/Camera2(고속 캡처는 기기 편차 큼) + **OpenCV** + MediaPipe.
- **장점:** 고fps 라이브 캡처·온디바이스 실시간 처리. 정확도·UX 우위.
- **단점:** 개발 비용↑, 기기별 카메라 스펙 파편화.

### 방식 C — 서버 분석 파이프라인
- 폰으로 촬영 → 업로드 → **Python(OpenCV + NumPy + SciPy)** 서버에서 정밀 분석.
- **장점:** 무거운 추적·피팅·모델 실행 자유로움, 알고리즘 검증에 최적.
- **용도:** MVP/프로토타입 알고리즘 검증 단계에 가장 적합.

**권장 경로:** 알고리즘 검증은 **C(파이썬 서버)**로 빠르게, 사용자 배포는
**A(웹 업로드형)** → 정확도·실시간이 필요하면 **B(네이티브)**로 승격.

## 7. 정확도 목표 vs 상용기

| 지표 | 본 시스템(폰 1대) | 트랙맨/GC |
|---|---|---|
| 헤드 스피드 | ±3% | ±1% |
| 스윙 패스 | ±1~2° | ±0.x° |
| 어택앵글 | ±2° | ±0.x° |
| 페이스 앵글 | ±3°+ (참고) | ±0.x° |
| 스핀 | 불가 | ◎ |
| 방향/비거리 | 모델 추정(오차 큼) | ◎ |

> 상용기가 앞서는 근본 이유: **레이더(도플러)** 또는 **듀얼 고속 카메라**로 3D 복원.
> 폰 1대는 2D 투영 오차가 원천적으로 남는다. 향후 **폰 2대(듀얼뷰)**로 확장하면
> 3D 복원이 가능해져 페이스·방향 정확도를 크게 끌어올릴 수 있다.

## 8. 단계별 로드맵

- **Phase 0 — 검증(PoC):** 파이썬으로 샘플 영상 1개에서 헤드 추적 → 헤드스피드·패스 산출.
  캘리브레이션 매트 1종 고정. 목표: "숫자가 나온다"를 증명.
- **Phase 1 — MVP:** 웹 업로드형. DTL 영상 → 패스 + 헤드스피드 + 궤적 오버레이. 신뢰구간 표기.
- **Phase 2 — 어택앵글:** 정면 뷰 지원, 로우포인트·어택앵글 추가. 뷰 자동 판별.
- **Phase 3 — 페이스(조건부):** 마커 부착 + 고fps 가이드, 페이스앵글 참고값 + 신뢰도 노출.
- **Phase 4 — 듀얼 카메라:** 폰 2대 동기화 → 3D 복원으로 정확도 도약.

## 9. 주요 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 모션블러(고속 헤드) | 검출 흔들림 | 밝은 조명·고fps, 서브픽셀 보정, 다중프레임 회귀 |
| 캘리브레이션 부정확 | 절대값 전부 왜곡 | 표준 매트/스틱 강제, 4점 호모그래피 |
| 카메라 정렬 오차 | 패스 각 편향 | 정렬 가이드 UI, 기준물 자동 검출 |
| 기기 fps 파편화(안드) | 측정 불가/부정확 | 지원 기기 화이트리스트, fps 자동 감지 경고 |
| 브라우저 고fps 캡처 제한 | 라이브 불가 | 녹화 후 업로드 분석 방식 채택 |
| 2D 투영 한계 | 방향·페이스 오차 | 참고값 표기, 듀얼카메라 로드맵 |

## 10. 요약

- **패스 · 어택앵글 · 헤드스피드**는 폰 슬로우모션으로 **충분히 실용적 측정 가능**.
- **페이스 앵글**은 마커+고fps 조건에서 **참고값 수준**까지.
- **스핀 · 정밀 비거리 · 3D 방향**은 폰 1대로는 **불가**(듀얼카메라/레이더 영역).
- 실행 전략: **파이썬 PoC로 알고리즘 검증 → 웹 MVP 배포 → 필요 시 네이티브/듀얼뷰 승격.**
- 정확도의 90%는 **캘리브레이션과 카메라 정렬**에서 결정된다.
